Receipt → Tax — an automation

STAGED WALKTHROUGH · SAMPLE DATA · NOT A LIVE CAPTURE

45 seconds, captions on screen, no audio. The supplier, ABN, card and accountant are sample data. The code is open source (MIT): github.com/ChinmayGit8765/receipt-tax ↗

01 · What it doesAdmin, off my plate

Take a photo of a receipt, say “log this receipt”, answer one question. Everything else is done for you.

The receipt is read and filed in the right Google Drive folder for the financial year. A row goes into that year's spreadsheet. A neatly formatted WhatsApp message to my accountant is ready to send, asking how much I can claim. When the accountant replies, I tell Claude, and the answer goes onto the same row. At tax time the spreadsheet is already complete.

It runs as a Claude skill, so it works the same from the Claude phone app, the web, the desktop app and Claude Code on my PC. The same skill also runs in OpenAI Codex, and a ChatGPT Custom GPT can call the same backend. They all write to one spreadsheet.

It's open source on GitHub under the MIT licence. Set it up with your own Google account (about 10 minutes), or use a local Excel file (about 1 minute).

02 · The pipelineFour hands, one flow

01
Claude

Reads the photo, asks “roughly, what's this for?”, tidies the answer and confirms once.

02
Files

The photo and the extracted record are packaged in Claude's code sandbox and sent on.

03
Google

An Apps Script backend checks for duplicates, files the photo in Drive and appends the row to the Sheet.

04
WhatsApp

A wa.me link opens a pre-filled draft. Nothing sends until I press send.

The split is deliberate. Claude does the three steps that need judgement: read, ask and clean, confirm. Everything mechanical runs in a small deterministic backend. Filing, naming, numbering, duplicate checks and the message template come out the same every time, whichever model or app made the request.

  • Never guess. Fields are copied exactly as printed. Anything missing or unreadable becomes null. Claude flags line items that don't add up, a missing GST line, or a missing ABN on an invoice over $82.50. It asks for a better photo instead of inventing a value.
  • Clean the wording, change nothing else. The purpose is fixed for spelling, grammar and punctuation only. No new facts, no “deductible”, no making it sound more persuasive. Private use stays in. The accountant sees what I actually said.
  • Idempotent by design. The backend hashes the photo (SHA-256) and also matches on supplier, date and total. Sending the same receipt twice gives back a “possible duplicate” (exit code 2), not a second row.
  • Safe concurrent writes. Each request runs under Apps Script's LockService, so two receipts sent at once still get sequential IDs (Tax26-27-0001, -0002…).
  • Rolls over automatically. The financial year comes from the receipt date. From 1 July the next year's folder and sheet are created the first time they're needed.
  • Token-gated and private. The web app only accepts requests that carry a secret token. The token lives in a git-ignored config.json, never in the repo, a prompt or this page. The backend has no delete action, so a leaked token can add rows but can't remove anything.
  • Human in the loop where it matters. One confirmation before anything is written. Messages are drafts you send yourself; the Discord and Slack webhooks only post after that confirmation.

Done by hand, one receipt can take a couple of hours from start to finish. You find the photo, rename it, work out which folder and year it belongs in, type the row, then write a message to your accountant that is clear enough to answer. Then you wait, and copy their answer back into the spreadsheet. Most of that happens outside work hours, which is exactly the time nobody wants to spend on admin.

The conversations with the accountant get easier too. Every message has the same layout: item, purpose, supplier and ABN, date, total with GST, and payment method. Every receipt has an ID and a filed photo they can open. They answer faster, with less back-and-forth, and their answer lands on the same row as the receipt it belongs to.

These figures are my own estimate from using it, not a controlled measurement. How much you save depends on how many receipts you have and how organised the manual process was to begin with.

05 · The patternWhere else this pays off

Receipts are just the example. The reusable shape is capture → structured record → file it → draft the follow-up, with a model making the judgement calls and a plain, deterministic backend doing the writing. The same shape fits a lot of everyday admin:

Business expenses

Photos to an expense sheet with categories, then a reimbursement email drafted for a manager or finance.

Supplier invoices

Due dates and amounts into a payables tracker, with a payment reminder drafted for the week each one is due.

Warranties & big purchases

Serial numbers, purchase dates and receipts stored together, ready when something breaks.

Small-business intake

Customer forms, job photos or quotes logged to a sheet, with a confirmation message ready to send.

Why it works: the expensive part of admin is context-switching, not typing. Taking a photo and answering one question takes seconds and fits into the moment you get the receipt. The automation handles everything that used to make you put it off. Nothing reaches another person without a human pressing send, so it is safe to hand over.

Want it for your own receipts? Clone the repo ↗, pick a client, a storage option and a messaging channel, and follow the quick start.

Limits, plainly: it's built for one person and their own storage. In the Claude app the sandbox needs network access to script.google.com. Reading accuracy depends on the photo, and a bad photo gets flagged rather than guessed. It doesn't give tax advice; the accountant decides what's claimable.
